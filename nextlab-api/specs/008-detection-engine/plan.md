# Implementation Plan: M8 — Detection Engine

**Branch**: `008-detection-engine` | **Date**: 2026-05-20 | **Spec**: `specs/008-detection-engine/spec.md`

**Input**: Feature specification from `specs/008-detection-engine/spec.md`

## Summary

M8 extends the existing M5 async worker to run a two-phase detection pipeline on every completed exam session: (1) a heuristic engine that scores behavioral trace events (tab switches, clipboard activity, heartbeat gaps) and stores the result immediately; (2) an LLM analysis that builds an enriched prompt from submission text + RAG context and calls the M6 AI router, storing the advisory result separately. Two new HTTP endpoints allow docentes to read the detection report and assign a grade (with mandatory override reason when outside the LLM-suggested range). Students are blocked at middleware from all detection data.

**Storage**: PostgreSQL 16 — new tables `analysis_results`, `grade_decisions` (migration 000008)

**Testing**: No test tasks generated (per spec decision)

**Target Platform**: Linux (Docker Compose, two-VPS deployment)

**Performance Goals**: Full detection pipeline ≤ 3 minutes from job enqueue to stored LLM result (SC-001, RNF-08)

**Constraints**:
- No new process — extends `cmd/worker/main.go` placeholder `processJob`
- `analysis_results` rows are INSERT-only (Principle I)
- `grade_decisions` rows are INSERT-only (Principle I)
- Student role blocked before DB query (Principle IV)
- Rubric injected in full, never fragmented (Principle V)
- LLM output labelled advisory only (Principle III)

**Scale/Scope**: One detection job per exam submission; ~100 concurrent students during peak exams at Unifranz

## Constitution Check

| Principle | Gate | Status |
|---|---|---|
| I — Immutable Evidence | `analysis_results` and `grade_decisions` are INSERT-only; no UPDATE/DELETE path exists | PASS |
| II — Async Analysis Isolation | Heuristic + LLM run exclusively in the M5 worker goroutine; HTTP upload handler is unaffected | PASS |
| III — Human Authority Over AI | LLM output is advisory; docente assigns final grade; override reason enforced at app layer; no auto-penalty | PASS |
| IV — Role-Based Data Isolation | Student role returns 403 at middleware before any DB query; docente scoped to own courses | PASS |
| V — Dual RAG Independence | Curricular and docente RAG called as separate `RetrieveService` method invocations; no cross-table JOIN | PASS |
| VI — Non-Invasive Auditing | No new trace capture; detection reads existing `trace_events` | PASS |
| VII — Submission Always Accepted | Detection is post-submission; filing analysis result never blocks or rejects the submission | PASS |

## Phase 0: Research

See `research.md` for 11 resolved decisions covering:
- Table creation strategy (analysis_results does not exist in M5)
- Two-row schema with UNIQUE constraint
- grade_decisions as separate table
- Worker dependency injection pattern
- Submission file retrieval via storage_key
- actividad_id derivation from exam_sessions join
- Heuristic scoring formula (additive, capped at 100)
- LLM prompt structure (JSON response format)
- Grade range override detection (5-point tolerance)
- Job trigger path (CloseSessionWithSubmission → processJob)
- HTTP endpoint design and student access denial
