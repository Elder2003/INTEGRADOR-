# Feature Specification: MW9 — Alerts & Analytics

**Feature Branch**: `009-mw9-alerts-analytics`

**Created**: 2026-05-27

**Status**: Draft

**Input**: User description: "lets do MW9"

---

## Overview

MW9 adds two complementary surfaces for docentes:

1. **Alerts** — Docentes see a list of system-generated alerts relevant to their activities (e.g., integrity flags, anomalous submissions, pipeline errors). Each alert can be individually dismissed. Dismissed alerts no longer appear in the active list.
2. **Analytics** — Docentes access two levels of statistics: per-activity analytics (grade distribution, submission breakdown) and per-course analytics (aggregated statistics across all activities in a course).

Co-docentes see the same analytics pages in read-only mode. Alerts are personal to each docente.

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Docente Views and Dismisses Alerts (Priority: P1)

A docente navigates to their alerts page and sees a list of unread/active alerts generated by the platform (integrity flags, AI-detected anomalies, pipeline errors, etc.). Each alert shows the activity it relates to, the type/severity, and a description. The docente can dismiss individual alerts, causing them to disappear from the active list. Dismissed alerts cannot be un-dismissed from the frontend.

**Why this priority**: Alerts are the docente's primary signal for items requiring attention. Without them, integrity concerns and pipeline failures go unnoticed.

**Independent Test**: Sign in as docente → navigate to alerts page → a list of active alerts is shown with title, activity reference, and date → click "Descartar" on one alert → the alert disappears from the list → reload → the dismissed alert is still absent.

**Acceptance Scenarios**:

1. **Given** a docente has active alerts, **When** they open the alerts page, **Then** all undismissed alerts are listed with type, activity name, description, and date.
2. **Given** a docente clicks "Descartar" on an alert, **When** the dismiss action succeeds, **Then** the alert is removed from the visible list immediately.
3. **Given** a docente has no active alerts, **When** they open the alerts page, **Then** an empty state message "Sin alertas activas." is shown.
4. **Given** a docente navigates back to the alerts page after dismissal, **When** the page loads, **Then** previously dismissed alerts do not reappear.
5. **Given** an alert is related to a specific activity, **When** the docente sees it in the list, **Then** a link to that activity is shown inline.

---

### User Story 2 — Docente Views Activity Analytics (Priority: P2)

A docente opens an activity's analytics page and sees statistics for that activity: total submissions, late submissions, grade distribution (score breakdown), and stage breakdown for investigation-type activities. All data is sourced directly from the backend and displayed read-only.

**Why this priority**: Activity-level analytics gives docentes the information they need for grading decisions and spotting systemic issues within a specific task.

**Independent Test**: Sign in as docente → open an activity with at least one graded submission → navigate to the activity analytics page → statistics are shown: submission count, late count, grade distribution chart/table, and (for informe activities) stage breakdown.

**Acceptance Scenarios**:

1. **Given** an activity with graded submissions, **When** docente opens the activity analytics page, **Then** total submissions, late submissions count, and grade distribution are displayed.
2. **Given** an activity of type "informe", **When** docente views analytics, **Then** a stage breakdown is also shown (count per stage: propuesta, desarrollo, revisión, aprobado).
3. **Given** an activity has no submissions, **When** docente views analytics, **Then** zeroed-out statistics are shown with an explanatory note.
4. **Given** a co-docente accesses the activity analytics page, **When** the page loads, **Then** the same read-only statistics are shown with no edit controls.
5. **Given** the backend returns a score distribution list, **When** the page renders, **Then** the grade distribution is displayed as a table with score ranges and counts, exactly as returned by the API.

---

### User Story 3 — Docente Views Course Analytics (Priority: P3)

A docente opens a course's analytics page and sees aggregated statistics across all activities in that course: total students, average grade, per-activity summary (name, submissions, average score), and overall grade distribution.

**Why this priority**: Course-level analytics enables docentes to compare activity difficulty and track overall cohort performance, but requires activity analytics to be meaningful.

**Independent Test**: Sign in as docente → open a course with multiple graded activities → navigate to course analytics page → summary shows each activity with its submission count and average grade, plus an overall grade distribution for the course.

**Acceptance Scenarios**:

1. **Given** a course with graded activities, **When** docente opens course analytics, **Then** a per-activity summary table is shown (activity name, submissions, average grade, late count).
2. **Given** a course with overall grade data, **When** docente views analytics, **Then** an overall score distribution for the course is displayed.
3. **Given** a course with no graded activities, **When** docente views course analytics, **Then** the page shows "Sin datos de calificaciones aún."
4. **Given** a co-docente accesses the course analytics page, **When** the page loads, **Then** the same statistics are displayed read-only.

---

### Edge Cases

- An alert refers to an activity the docente can no longer access (deleted or removed from roster) — the alert still shows the activity name as plain text (no link).
- Grade distribution contains a single score bucket — displayed as a single-row table without visual issues.
- Course analytics aggregated across 50+ activities — the per-activity table is scrollable; no pagination required for the initial version.
- Alert dismiss fails (network error) — the alert remains visible and an inline error message is shown next to the dismiss button.
- Analytics page loaded while backend is computing stats — a loading state is shown; if the backend returns empty data, the page renders the zero-state gracefully.
- Co-docente should not see the docente's personal alert list — alerts are only accessible at `/docente/...` routes.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The docente portal MUST include an alerts page accessible from the navigation that lists all undismissed alerts for the authenticated docente.
- **FR-002**: Each alert MUST display: alert type, severity level, description, activity name (linked to the activity when accessible), and creation date.
- **FR-003**: Each alert MUST have a "Descartar" button that, when clicked, dismisses the alert and removes it from the active list.
- **FR-004**: The alerts list MUST show a "Sin alertas activas." empty state when no undismissed alerts exist.
- **FR-005**: The docente activity detail page MUST include a link to the activity analytics page.
- **FR-006**: The activity analytics page MUST display: total submissions, late submissions count, and grade distribution as returned by the backend API.
- **FR-007**: For activities of type "informe", the activity analytics page MUST additionally display a stage breakdown (count per investigation stage).
- **FR-008**: The course detail page (docente) MUST include a link to the course analytics page.
- **FR-009**: The course analytics page MUST display: a per-activity summary table and an overall grade distribution for the course.
- **FR-010**: Both analytics pages MUST handle empty states (no data) with a clear explanatory message.
- **FR-011**: Both analytics pages MUST be accessible to co-docentes at their `/codocente/...` route equivalents, read-only (no edit controls exist on analytics pages).
- **FR-012**: Analytics data MUST be rendered exactly as returned by the API — no aggregation, computation, or transformation on the client.

### Key Entities

- **Alert**: A system-generated notification for a docente; has `id`, `type`, `severity`, `description`, `actividad_id`, `actividad_title`, `created_at`, `is_dismissed`. Only undismissed alerts are shown in the active list.
- **ActivityAnalytics**: Statistics for a single activity; has `total_submissions`, `late_submissions`, `grade_distribution` (list of score-range buckets with counts), `stage_breakdown` (optional, for informe activities).
- **CourseAnalytics**: Aggregated statistics for a course; has `activity_summaries` (list with activity name, submission count, average grade, late count) and `overall_grade_distribution`.

---

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Docente can view their full alerts list within 3 seconds of navigating to the page.
- **SC-002**: Dismissing an alert removes it from the visible list within 1 second of clicking "Descartar" — confirmed by manual smoke test.
- **SC-003**: Activity analytics page loads and displays complete statistics within 3 seconds — confirmed across at least 3 different activities.
- **SC-004**: Course analytics page correctly aggregates and displays data for a course with 5 or more activities without layout issues.
- **SC-005**: Co-docente can access both analytics pages without being redirected or shown an error.
- **SC-006**: All three new pages (alerts, activity analytics, course analytics) correctly display empty states when no data is available.

---

## Assumptions

- Alerts are generated entirely by the backend (M9) — the frontend never creates, modifies, or computes alert conditions. Dismiss is the only write operation from the client.
- Alert types and severity levels are strings returned by the API — the frontend displays them as-is without mapping to icons or colors beyond basic severity styling (e.g., distinguishing high/medium/low).
- Activity analytics and course analytics are pre-computed by the backend (M10, M12) — the frontend requests them and renders the response. No charting library is used; grade distribution is displayed as a table.
- The alerts page is a docente-only feature — co-docentes do not have an alerts page. Only the analytics pages are shared with co-docentes.
- Links to the activity analytics page are added to the existing docente `ActividadDetailPage`; links to the course analytics page are added to the existing docente `CursoDetailPage`.
- Alert `actividad_title` is included in the API response so the frontend can display the name without a separate fetch.
- The grade distribution from the API is a list of `{ range_label: string, count: number }` objects (e.g., `{ range_label: "90-100", count: 5 }`).
- Co-docente analytics routes use the same page components as the docente routes (different URL prefix only), matching the pattern established in MW5–MW8.
